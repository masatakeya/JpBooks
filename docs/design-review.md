## 0. 結論（先に3行）

1. **リポジトリに TypeScript ソースが存在しない。** バンドル済み `main.js` だけがコミットされており、これ以上の設計改善は物理的に不可能。ソースとビルドの復旧が全ての前提。


## 2. データ取得アーキテクチャ —— 設計思想と実装の乖離

### 2.1 README の記述が実装と一致していない

README 3章はこう宣言しています。

> openBD で書籍情報が**取得できた場合**はその結果を使用する。openBD で情報が**取得できなかった場合のみ**、NDL Search に問い合わせる。

しかし `searchOpenBDByTitle`（`main.js:325-341`）の実際の流れは逆です。

```
searchByTitle(title)
  └─ searchOpenBDByTitle(title)
       ├─ fetchFromNDL(title)          ← まず NDL で候補を取る（必ず実行）
       └─ 候補の先頭10件について
            └─ fetchFromOpenBD(isbn)   ← 1件ずつ openBD を叩いて詳細を上書き
```

これは「フォールバック」ではなく「**NDL で探し、openBD で肉付けする**」という別のパターンです。しかも、そうならざるを得ない理由があります —— **openBD には書名検索 API が無く、ISBN 引きしかできない**からです。つまり README の設計方針は、書名検索に関しては最初から実現不可能なものを書いています。

問題は文書の不正確さだけではありません。**設計の言葉が実態を表していないので、この先の意思決定を誤らせます。** 実際、README 5章の設定項目「APIの優先順位」は未実装のままです（設定画面にあるのは保存先・ファイル名・テンプレートの3つのみ）。「優先順位」という概念自体が、検索と詳細取得を区別しない前提から出てきたものです。

### 2.2 N+1 リクエスト

書名検索1回あたり、**NDL 1回 + openBD 最大10回を逐次実行**します（`main.js:330-339`、`await` がループ内）。日本語の書名は候補が多く、体感で数秒かかる構造です。

openBD の `/v1/get` は ISBN のカンマ区切り複数指定に対応しているため（要実測）、**10回の逐次リクエストは1回のバッチリクエストに畳めます**。ここは設計というより実装の取りこぼしですが、後述の Provider 分離をすると自然に「一括取得」の形に落ちます。

### 2.3 NDL のエンドポイントが README と違う

- README 3章: `https://iss.ndl.go.jp/api/opensearch`（**旧ドメイン。2024年のNDLサーチ刷新で廃止**）
- 実装 `main.js:215`: `https://ndlsearch.ndl.go.jp/api/opensearch`（現行）

実装は正しく、README が古い。コミット `c582959` で `any=` → `title=` のパラメータ修正が入っているので、この領域は実際に不具合を踏んで直した形跡があります。

### 2.4 検索結果の重複排除がない

NDL は同一書籍の版違い・刷違いを別レコードで返します。重複除去も、版のグルーピングもしていないため、候補リストに同じ書名が並びます。ISBN-13 に正規化したキーでの dedupe が必要です。

### 2.5 ISBN 判定が甘い

```js
var ISBN_REGEX = /^(97[89])?\d{9}[\dX]$/;
```

- チェックディジットを検証していないので、**任意の10桁数字が ISBN 扱い**になります（書名が数字のみのケースで誤判定）
- ISBN-10 を ISBN-13 に変換していません。openBD 側が吸収してくれる可能性はありますが（要実測）、依存すべきではありません
- 全角数字・ハイフン以外の区切りを正規化していません

### 2.6 エラーが「0件」に化ける

`fetchFromOpenBD` は `catch` で `null`、`fetchFromNDL` は `catch` で `[]` を返します（`main.js:193-196`, `276-279`）。結果、**ネットワーク断・API障害・XMLパース失敗のすべてが「書籍が見つかりませんでした」と表示されます**。ユーザーは自分の入力が悪いと思ってしまう。エラー種別を型として持ち上げ、UI で区別すべきです。

### 2.7 取得メタデータが薄い

現在の `Book` は title / subtitle / author / authors / publisher / published / isbn / description のみ。読書ノートという用途を考えると、openBD が持っている情報を捨てています。

- **表紙画像 URL**（`summary.cover`）—— 読書ノートで最も欲しい要素のひとつ
- ページ数、シリーズ名、価格、判型（ONIX の `DescriptiveDetail` 配下）
- NDC 分類、件名（NDL 側が持つ）

`description` に openBD の HTML タグが混入しうる点も未処理です。

## 3. UI 層 —— `SuggestModal` の再発明

`BookSearchModal`（`main.js:345-496`）は `Modal` を継承し、input・候補リスト・キーボードナビゲーション・選択ハイライト・スクロール追従を全て手書きしています。これは Obsidian が `SuggestModal<T>` として提供している機能そのものです。

### 3.1 選択ハイライトが壊れている（バグ）

```js
updateSelection(scroll = true) {
  const items = this.listEl.querySelectorAll("div");   // ← 全ての子孫 div
  items.forEach((el, i) => {
    el.style.background = i === this.selectedIndex ? "var(--background-modifier-hover)" : "";
  });
```

`renderList`（`main.js:434-456`）では、候補1件につき **行 div + 書名 div + メタ div の計3つの div** を生成しています。したがって `querySelectorAll("div")` が返すのは件数の3倍の要素で、ドキュメント順は

```
[0] 行0  [1] 書名0  [2] メタ0  [3] 行1  [4] 書名1  [5] メタ1 ...
```

`selectedIndex = 1`（↓キー1回）で背景色が付くのは **1件目の書名テキストだけ**です。2件目の行はハイライトされません。`scrollIntoView` も同じく誤った要素に対して呼ばれます。マウスホバー側は `selectedIndex = i`（候補のインデックス）を入れるので、キーボードとマウスで指しているものが食い違います。

コミット `e0ff13a` はホバー時の `scrollIntoView` を止める修正でしたが、根本にあるこのインデックス不整合は残っています。

**修正**: 行 div を配列として保持するか `listEl.children` を使う。あるいは `SuggestModal` に載せ替えて問題ごと消す。

### 3.2 IME（日本語入力）を考慮していない

```js
async handleKeyDown(e) {
  if (e.key === "Enter") { ... this.choose(...) / this.runSearch() }
```

`e.isComposing` を見ていません。**日本語書籍を検索するプラグインで、変換確定の Enter が検索実行や候補決定として解釈される**という致命的な使い勝手の問題です。「げんだい」→変換→Enter確定 の Enter で検索が走る、あるいは候補が既に出ていればモーダルが閉じてノートが作られます。

さらに `e.key.length === 1 || e.key === "Backspace"` で結果をクリアする分岐（`main.js:399-401`）も、IME 経由の入力では発火しません（変換中は `key` が `"Process"`）。

### 3.3 インラインスタイルの全面使用

`style.cssText = "..."` と `el.style.xxx = ...` が UI コード全域にあります（設定画面の `textareaEl` だけで15行）。Obsidian のコミュニティプラグインレビューでは **JavaScript でのスタイル指定を避け `styles.css` にクラスとして書く**ことが明確に求められており、現状のままでは申請が通りません。テーマ側からの上書きも効きません。

### 3.4 設定画面の細かい規約違反

- `containerEl.createEl("h2", { text: "JpBooks 設定" })` —— 設定タブの先頭に見出しを置かないのが現行ガイドライン（プラグイン名は Obsidian 側が表示する）
- テンプレート textarea の `input` イベントで**キーストロークごとに `saveData()`**（`main.js:126-129`）。1文字ごとにディスク書き込みが走ります。debounce 必須
- コマンド名 `"Search and Insert"` は sentence case（`Search and insert`）が推奨

### 3.5 検索のキャンセルができない

`isSearching` フラグで**新しい検索を捨てる**設計です（`main.js:409-410`）。ユーザーが打ち直しても前の検索が終わるまで反応しません。`AbortController` で前のリクエストを中断する方が正しい。

## 4. テンプレート層

### 4.1 YAML エスケープがない

```js
const vars = { title: book.title, ... };
result = result.replace(new RegExp(`\\{\\{${key}\\}\\}`, "g"), value);
```

デフォルトテンプレートは `title: "{{title}}"` という形なので、**書名に `"` が含まれると frontmatter が壊れます**。`description` は改行を含むのが普通なので、frontmatter に置いた瞬間に壊れます。テンプレート変数は「文字列の穴埋め」ではなく「YAML 値として安全な形に整形して差し込む」必要があります（引用符のエスケープ、複数行はブロックスカラー `|`）。

### 4.2 `{{authors}}` の出力が README と違う

README 4章は `authors: ["著者1", "著者2"]` と書いていますが、実装（`main.js:512`）が生成するのは括弧なしの `"著者1", "著者2"` です。ユーザーがテンプレートに `authors: [{{authors}}]` と自分で書かないと配列になりません。ドキュメント通りに書くと壊れます。

### 4.3 置換が多段で走る

`replace` を変数ごとに `result` 全体へ順次適用しているため、**先に差し込まれた書籍データの中に `{{author}}` のような文字列があると、それも置換されます**。実害は稀ですが、1パスで走査して置換する実装（`replace(/\{\{(\w+)(?::([^}]+))?\}\}/g, ...)`）に統一すべきです。

### 4.4 ファイル名生成が不十分

```js
return rendered.replace(/[\\/:*?"<>|#^[\]]/g, "").trim();
```

- 長さ制限なし → 日本語の長い書名（UTF-8で1文字3バイト）でファイルシステムの上限を超え、`vault.create` が不明瞭なエラーで落ちます
- 先頭・末尾のドット、Windows の予約名（`CON`, `NUL` 等）が未処理
- 全部除去されて空文字になると `.md`（隠しファイル）が生成されます

### 4.5 「挿入」と「ノート作成」で同じテンプレートを使っている

`search-and-insert` は `editor.replaceSelection(renderTemplate(this.settings.template, book))` を実行します（`main.js:536-541`）。設定されているテンプレートは frontmatter 付きなので、**既存ノートのカーソル位置に `---` 区切りの YAML ブロックが丸ごと挿入されます**。これは常に間違った出力です。用途ごとにテンプレートを分けるか、挿入時は frontmatter を落とす必要があります。

## 5. 再設計案

### 5.1 データ層: 「検索（discovery）」と「詳細取得（enrichment）」を分ける

現状の混乱の原因は、性質の違う2つの操作を「APIの優先順位」という1本の軸で扱おうとしたことにあります。分けます。

```
┌─ SearchProvider ──────────────┐   キーワード → 候補（ISBN を含む軽量レコード）
│  NDLSearchProvider            │   ・openBD は書名検索ができないので、ここには入らない
│  RakutenBooksProvider (将来)  │   ・複数プロバイダの結果を ISBN-13 でマージ・dedupe
│  GoogleBooksProvider  (将来)  │
└───────────────────────────────┘
              ↓ ISBN[]
┌─ MetadataProvider ────────────┐   ISBN[] → 詳細レコード（バッチ取得）
│  OpenBDProvider  (優先度 1)   │   ・ここで初めて「優先順位」が意味を持つ
│  NDLProvider     (優先度 2)   │   ・フィールド単位のマージ（空欄を下位で補完）
└───────────────────────────────┘
              ↓
        BookRecord（正規化済み）
```

インターフェース案:

```ts
interface SearchProvider {
  readonly id: string;
  search(query: string, signal: AbortSignal): Promise<BookCandidate[]>;
}

interface MetadataProvider {
  readonly id: string;
  fetchByIsbn(isbns: string[], signal: AbortSignal): Promise<Map<string, Partial<BookRecord>>>;
}
```

これで得られるもの:

- README 5章が約束している「APIの優先順位」設定が、**詳細取得側の並べ替えとして自然に実装できる**
- `fetchByIsbn` が配列を受ける形なので、openBD のバッチ取得が前提になり N+1 が構造的に発生しない
- 楽天ブックス（内容紹介が充実）や Google Books の追加が、既存コードを触らずに済む
- ISBN 検索は「SearchProvider をスキップして MetadataProvider に直行」という特殊ケースとして素直に書ける

マージ戦略は**フィールド単位**にします。「openBD が勝つ」ではなく「`description` は openBD 優先、`title` は NDL 優先（正式書名が入る）、空欄は下位プロバイダで補完」といった粒度。

### 5.2 横断的な関心事

| 項目 | 方針 |
|---|---|
| キャッシュ | ISBN → BookRecord のメモリ LRU。同一セッション中の再検索を無通信に |
| 中断 | `AbortController` を Provider の引数に通す。入力が変わったら前の検索を中断 |
| デバウンス | 入力から 300ms でインクリメンタル検索（現在の「Enter で検索」も残す） |
| エラー | `Result<T, SearchError>` 型で「0件」「ネットワーク」「パース失敗」を区別し、Notice の文言を変える |
| ログ | `console.log` の直書きをやめ、デバッグ設定で切り替え可能なロガーへ |

### 5.3 UI 層: `SuggestModal` へ載せ替え

`SuggestModal<BookRecord>` を継承し、`getSuggestions` / `renderSuggestion` / `onChooseSuggestion` の3メソッドに集約します。キーボードナビ、ハイライト、スクロール追従、IME 対応（Obsidian 側で処理済み）、アクセシビリティが全て標準の挙動になり、**3.1 と 3.2 のバグはコードごと消えます**。

`renderSuggestion` で表紙サムネイル（openBD の `summary.cover`）と「出版社・出版年」を出せば、版の選び分けもできます。スタイルは全て `styles.css` のクラスへ。

### 5.4 テンプレート層

- 単一パスのトークナイザに置き換え、`{{name}}` / `{{name:filter}}` を統一処理
- **値の出力コンテキストを意識する**: frontmatter 内は YAML セーフに、本文はそのまま
- `{{authors}}` は YAML リストとして出力（README の記述に実装を合わせる）
- フィルタ: `{{title:kebab}}`, `{{published:YYYY}}`, `{{description:blockquote}}` など
- **テンプレートを2種類に分離**: `noteTemplate`（ノート新規作成用、frontmatter あり）と `insertTemplate`（カーソル挿入用、frontmatter なし）
- ファイル名は正規化ユーティリティに集約（長さ制限・予約名・空文字フォールバック）

### 5.5 テスト

ネットワークに依存しない純粋関数から始めれば、すぐに書けます（vitest 想定）。

- ISBN 判定・ISBN-10→13 変換・チェックディジット
- 日付正規化（`normalizeDate` が2ファイルに重複している点も解消）
- テンプレート描画（YAML エスケープ、複数行、フィルタ）
- ファイル名サニタイズ（境界ケース）
- Provider マージ戦略（固定 JSON/XML フィクスチャ）

## 6. 進め方の提案

| **0** | `main.js` から TypeScript ソースを復元し、ビルド環境・`.gitignore`・`versions.json`・CI を整備 | **これが無いと以降が着手できない** |
